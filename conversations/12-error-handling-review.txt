  1. VERDICT

  Error handling is partial but deliberate on the request path and absent on the
  data-script path.

  Top risks
  1. load_orders runs TRUNCATE before it checks that there is anything to load.
     A header-only or all-invalid CSV empties orders (F1).
  2. The loader's summary crashes after the commit whenever there are zero
     rejects, so it exits 1 with data loaded (F2).
  3. Several unhandled paths return a plain-text 500 outside the error contract:
     - Cell types the schema does not model.
     - A validator RecursionError.
     - SQLAlchemy errors that are not DBAPI errors.
     - A bad LLM_BASE_URL.

     Separately, every SQLSTATE-bearing database fault is reported as a 400 that
     blames the LLM's SQL (F3–F5).

  Top strengths
  1. The LLM client translates errors at its boundary into a typed hierarchy and
     has no unwrapped exception paths, apart from the InvalidURL case in F9.
  2. The validator is closed-world. It fails closed on every probe, and the
     typed rejections have extensive adversarial tests.
  3. Execution uses layered safety: a read-only transaction, a SET LOCAL
     statement timeout, a row cap and context-managed connections. The loader's
     single transaction is atomic by construction.

  5. FINDINGS

  F1 — Loader empties orders when nothing cleans successfully

  - Severity: Critical (data integrity)
  - Scenarios: F1, F4, X1, D7
  - Evidence: scripts/load_orders.py:32-34:
  conn.execute(text("TRUNCATE orders RESTART IDENTITY"))
  if not clean.empty:
      conn.execute(INSERT_SQL, clean.to_dict("records"))
    Line 36 only compares loaded to len(clean), and both are 0.
  - Failing input: a header-only CSV, or a CSV where every row is invalid (e.g.
    bad,,Atlantis,,x,zzz). Verified in-memory: clean.empty is True. The DB step
    itself was not run.
  - Impact: the previous data is destroyed and the loader exits 0. /query then
    returns 200 with rows: [], which looks like a legitimate empty answer.
  - Direction: abort before TRUNCATE when the cleaned set is empty or the reject
    ratio exceeds a threshold.

  F2 — Loader summary crashes after commit when there are zero rejects

  - Severity: High
  - Scenarios: F3, F7, X2
  - Evidence: load_orders.py:59: by_reason = 
    rejects["reason"].str.split(";").explode().value_counts(). Verified:
    AttributeError: Can only use .str accessor with string values, not floating
    for header-only, all-valid, and any zero-reject input.
  - Impact: the transaction has already committed at :55. The script exits 1
    with data loaded, and the compose command generate_orders && load_orders
    reports failure. The default seeded data has rejects, so the normal run
    hides this.
  - Direction: the empty-reject case needs a dtype-safe summary.

  F3 — Infrastructure SQLSTATE faults reported as 400 against the LLM's SQL

  - Severity: High
  - Scenarios: D1, D2, X3, E3
  - Evidence: repository.py:82-83: detail = f" (SQLSTATE {sqlstate})" if 
    sqlstate else "" followed by return QueryFailedError(f"the database rejected
    the query{detail}"). query_service.py:45-46: except QueryFailedError as 
    exc: raise GeneratedSQLError("query_failed", exc.reason, sql). Only 57014 is
    special-cased (:78).
  - Failing input: a valid question when the loader has not run yet (42P01,
    undefined table or view), when app_ro lacks a grant (42501), or on
    57P01/53200. The code settles the mapping; live behavior is UNVERIFIED.
  - Impact: operator faults return a client-error 400 with sql echoed, and
    nothing is logged. The README's own run order has the API up before the
    loader.
  - Direction: classify SQLSTATE classes 42P01, 42501, 53 and 57 as
    QueryExecutionError, not QueryFailedError.

  F4 — Validator-accepted SQL whose result cannot be serialized returns a 
  plain-text 500

  - Severity: High
  - Scenarios: D6, X4, A5
  - Evidence: schemas.py:11: Cell = str | int | float | Decimal | date | 
    datetime | bool | None. routers/query.py:68 builds QueryResponse(...)
    outside the try. Verified: the validator accepts SELECT array_agg(customer) 
    FROM orders and SELECT now() - order_date FROM orders. With a fake
    repository, a list or timedelta cell → 500 text/plain. NaN, Inf and Decimal
    NaN are silently emitted as null.
  - Impact: a plausible LLM query executes and then 500s. NaN → null is a silent
    change of value.
  - Direction: map unsupported cell types to a typed error (or stringify them).

  F5 — Validator misses RecursionError

  - Severity: Medium
  - Scenarios: C7, C8, E1
  - Evidence: validator.py:34-37: except SqlglotError as exc: raise 
    InvalidSQLError("could not parse SQL"). Verified: "SELECT " + "("*50 + "1" +

    500 instead of a 400 invalid_sql. traverse_scope and normalize_identifiers
    at :49-50,69-74 are also unguarded; I found no failing input for them.
  - Direction: catch RecursionError and the scope errors at the validator
    boundary.
