     Step 7: /query endpoint

     Context

     Steps 0–6 are in place: data loaded, views, validate_sql
     (app/validator.py), LLMClient + LlamaCppClient (app/llm/), app_ro role
     (read-only by default, statement_timeout=5s), create_engine_from_env
     (app/db/connection.py). main.py is still the stub. Step 7 connects them:
     question → LLM → validate → execute as app_ro → JSON, with typed errors
     mapped to the PLAN §3 contract. Step 8 (hermetic endpoint tests) overrides
     the LLM and repository with dependency_overrides, so the dependency seams
     are designed in this step.

     Decisions

     - Sync throughout. The LLM client (httpx.Client) and SQLAlchemy are sync,
       so the route is a plain def and FastAPI runs it in its threadpool. No
       async rewrite.
     - Dependency providers (app/dependencies.py): get_llm_client() and
       get_query_repository() are functools.lru_cache singletons built lazily
       from env (create_llm_client_from_env,
       create_engine_from_env("READONLY_DATABASE_URL")).
       get_query_service(llm=Depends(...), repo=Depends(...)) builds the
       service. Lazy creation means importing the app needs no env or network,
       which step 8 needs. Trade-off: a missing env var shows up as a 500 on the
       first request, not at startup. Noted in the README.
     - Repository protocol, same pattern as LLMClient:
       QueryRepository.run_select(sql) -> QueryResult(columns, rows, truncated).
       PostgresQueryRepository(engine) is the only code that touches the DB.
     - Execution (PostgresQueryRepository.run_select):
       - with engine.connect() as conn, conn.begin(): then SET TRANSACTION READ 
         ONLY and SET LOCAL statement_timeout = '5s'. Both are set explicitly so
         safety doesn't depend only on the role defaults (defense in depth).
       - The SQL runs via conn.exec_driver_sql(sql), not text(sql). text() would
         treat any :word inside the LLM's SQL as a bind parameter. Run with no
         parameters, psycopg does no % interpolation, so LIKE '%x%' passes
         through unchanged. Verify early with a LIKE '%a%' query.
       - Row cap: fetchmany(MAX_ROWS + 1) with MAX_ROWS = 1000 sets truncated.
         The SQL is not rewritten, so the validator's normalized SQL is exactly
         what runs.
       - Exceptions become typed QueryExecutionError(reason) subclasses:
         - SQLSTATE 57014 (query_canceled) → QueryTimeoutError
         - OperationalError with no SQLSTATE (connection failure) →
           DatabaseUnavailableError
         - any other DBAPIError → QueryFailedError, with a safe message carrying
           the SQLSTATE class, not the raw Postgres text
     - Service (app/services/query_service.py): QueryService(llm, 
       repo).answer(question) -> QueryAnswer(sql, columns, rows, truncated). It
       calls llm.generate_sql → validate_sql → repo.run_select(validated). It
       wraps InvalidSQLError and QueryFailedError into GeneratedSQLError(code, 
       reason, sql) so the router can return the offending SQL. LLMError and the
       other execution errors propagate unchanged.
     - Router (app/routers/query.py): POST /query. It catches the typed errors
       and returns JSONResponse(ErrorResponse). HTTP concerns stay in the router
       only. Error bodies are declared in responses= so OpenAPI documents them.

     - Schemas (app/schemas.py):
       - QueryRequest.question: Annotated[str, 
         StringConstraints(strip_whitespace=True, min_length=1, max_length=500)]
       - QueryResponse: question, sql, columns: list[str], rows: 
         list[list[Cell]], truncated: bool, where Cell = str | int | float | 
         Decimal | date | datetime | bool | None. No Any. Pydantic serializes
         Decimal as a JSON string ("8084.52"), which keeps money exact. My call;

       - ErrorResponse: code, message, sql: str | None.

     - App factory (app/api.py): create_app() registers the router and moves the
       existing GET / and GET /health unchanged. main.py becomes from app.api 
       import create_app; app = create_app().

  Two assumptions in my plan turned out wrong, and testing caught both:
  - % in the SQL: psycopg reads % as a placeholder start even when no parameters
    are passed, so LIKE '%a%' failed. The repository now escapes % to %% before
    executing.
  - Error mapping: that failure first came back as a 503, because any error
    without a SQLSTATE was mapped to db_unavailable. Now only connection-type
    errors (OperationalError, InterfaceError) map to 503. Anything else Postgres
    rejects becomes 400 query_failed, as you decided.
