     Step 9 — Containerize the API

     Context

     PLAN.md §4 step 9: the API must run as a compose service next to llm and db
     (user decision). Today only llm/db run in compose; the API runs on the
     host via uv run fastapi dev. Root .env holds host URLs (127.0.0.1), so the
     container cannot reuse them as-is. Data is loaded into pgdata by the
     loader, never baked into the image.

     User decisions (this session): scripts generate the CSV in-container (no
     bind mount; generator is seeded, so data equals the host run); clean-volume
     verification approved (wipe test_pgdata).

     Facts checked

     - uv 0.9.16 locally → pin ghcr.io/astral-sh/uv:0.9.16; Python 3.14.8
       locally, requires-python >=3.14 → python:3.14-slim.
     - pyproject.toml has no [build-system] (virtual project); uv.lock present;
       fastapi-cli + uvicorn are locked via fastapi[standard].
     - POSTGRES_USER/PASSWORD/DB, APP_RO_PASSWORD in .env are URL-safe (no
       encoding needed when interpolated into URLs; README caveat in step 10).
     - Env readers already exist: app/db/connection.py:create_engine_from_env,
       app/llm/client.py:create_llm_client_from_env. No code changes needed.
     - GET /health exists (app/api.py:16) → reused for the container
       healthcheck.

     Changes

     1. coding_assesment/Dockerfile (new)

     uv's documented two-stage-sync pattern (dependency layer cached separately
     from source):
     FROM python:3.14-slim
     COPY --from=ghcr.io/astral-sh/uv:0.9.16 /uv /uvx /bin/
     ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=0 \
         PATH="/app/.venv/bin:$PATH"
     WORKDIR /app
     RUN --mount=type=cache,target=/root/.cache/uv \
         --mount=type=bind,source=uv.lock,target=uv.lock \
         --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
         uv sync --locked --no-install-project --no-dev
     COPY . /app
     RUN --mount=type=cache,target=/root/.cache/uv uv sync --locked --no-dev
     RUN useradd --system --uid 10001 app && mkdir -p /app/data && chown app
     /app/data
     USER app
     EXPOSE 8000
     CMD ["fastapi", "run", "main.py", "--host", "0.0.0.0", "--port", "8000"]
     Non-root user; only data/ writable (generator/loader output).

     2. coding_assesment/.dockerignore (new)

     .venv, __pycache__/, *.py[oc], .pytest_cache/, .ruff_cache/, data/, tests/,
     .env*, Dockerfile, .dockerignore.

     3. docker-compose.yml — add services (replace the now-obsolete "Add further
     services below" comment)

     - api: build: ./coding_assesment, image: orders-api:local, restart: 
       unless-stopped, ports: ["127.0.0.1:8000:8000"], networks: [backend],
       depends_on llm + db with condition: service_healthy. environment
       (explicit; no env_file, so host URLs never leak in):
       - LLM_BASE_URL: http://llm:8080/v1
       - READONLY_DATABASE_URL: postgresql+psycopg://app_ro:${APP_RO_PASSWORD:?…
         }@db:5432/${POSTGRES_DB:-orders}
       - healthcheck: python -c "import urllib.request; 
         urllib.request.urlopen('http://localhost:8000/health')" (slim image has
         no curl).
     - loader (deviation from PLAN wording, flagged): same image: 
       orders-api:local + build, profiles: [tools], depends_on: db: 
       service_healthy, networks: [backend], environment: DATABASE_URL: 
       postgresql+psycopg://${POSTGRES_USER:-orders}:${POSTGRES_PASSWORD:?…}@db:
       5432/${POSTGRES_DB:-orders}, command: ["sh", "-c", "python -m 
       scripts.generate_orders && python -m scripts.load_orders"].
       - Why: PLAN says docker compose run --rm api python -m 
         scripts.load_orders, which would require the long-running API container
         to carry the owner credentials — contradicts the least-privilege
         design (app_ro). A profile-gated one-shot service keeps owner creds out
         of the API. Run: docker compose run --rm loader. Not started by up.
