     Step 6: LLM client behind an interface

     Context

     Step 7 (/query) and step 8 (endpoint test with a mocked LLM) need an
     LLMClient interface, so the service never depends on llama.cpp directly.
     Planned commit: feat: LLM client behind interface.

     Probe of the running llm service (read-only calls, done during planning).
     It settles the PLAN §2 risk about thinking output:

     ┌─────────────────────────────┬──────────────────────────────────────┐
     │            Mode             │                Result                │
     ├─────────────────────────────┼──────────────────────────────────────┤
     │                             │ content: ""; reasoning goes to       │
     │ default (thinking on)       │ reasoning_content; hit               │
     │                             │ finish_reason: length at 400 tokens; │
     │                             │  82 s                                │
     ├─────────────────────────────┼──────────────────────────────────────┤
     │ chat_template_kwargs:       │ content = bare SQL, finish_reason:   │
     │ {"enable_thinking": false}  │ stop, 45 tokens, 10 s                │
     └─────────────────────────────┴──────────────────────────────────────┘

     The model's output with no context was wrong: it used year 2023 and had no
     status='completed' filter. The prompt therefore has to state the data year,
     the sales definition, and the valid values. sqlglot's validator already
     accepts a trailing ; (verified), so the client does not strip it.

     Design (my calls; alternatives in brackets)

     - Thinking off through chat_template_kwargs (needs --jinja, already in
       compose). The <think>…</think> strip stays as a defensive fallback.
       [Thinking on was rejected because it is 8× slower and gets truncated.]
     - Sync httpx.Client [not async]. The endpoints will be sync def on sync
       SQLAlchemy, so FastAPI's threadpool handles concurrency. httpx 0.28.1
       already ships with fastapi[standard], so no new deps.
     - temperature=0, max_tokens=512, timeout 60 s (one constant each). No model
       field: llama-server serves a single model.

     Files (all new under coding_assesment/)

     1. app/llm/__init__.py: empty.
     2. app/llm/base.py:
        - class LLMClient(Protocol): def generate_sql(self, question: str) -> 
          str: ...
        - Error hierarchy, with reason safe to show, in the same pattern as
          InvalidSQLError in app/validator.py: LLMError(Exception) →
          LLMUnavailableError (connect error / non-2xx → 502), LLMTimeoutError
          (→ 504), LLMResponseError (bad JSON, missing choices, empty content,
          finish_reason == "length" → 502). The HTTP mapping happens in step 7.
          The original exception is always kept with raise … from exc.
        - extract_sql(content: str) -> str: pure. Strips <think>…</think> and
          ```sql fences, then trims. Empty → LLMResponseError.
     3. app/llm/prompt.py (one module beyond the PLAN §3 layout; reason: the
        prompt is provider-agnostic and testable on its own):
        build_messages(question) -> list[dict[str, str]]. The system prompt
        contains:
        - the schema of only orders, v_sales_by_month_country and
          v_top_customers (columns and types, from schema.sql/views.sql)
        - the PostgreSQL dialect, data range 2025-01-01…2025-12-31 ("March" =
          2025-03), sales = status = 'completed', and "prefer the views"
        - valid countries/statuses imported from app.cleaning.COUNTRIES /
          VALID_STATUSES (reuse, no duplication)
        - output rules: one SELECT, no prose, no comments
        - 3 few-shot pairs: Spain/March via the view, top customers via the
          view, a count by status on orders
     4. app/llm/client.py: LlamaCppClient(base_url, http: httpx.Client | None = 
        None) posts to {base_url}/chat/completions, maps
        httpx.TimeoutException/ConnectError/HTTPStatusError/JSON errors to the
        typed errors, and returns extract_sql(content).
        create_llm_client_from_env() reads LLM_BASE_URL and raises RuntimeError
        if it is unset, mirroring create_engine_from_env in
        app/db/connection.py.
     5. tests/test_llm_client.py (hermetic: httpx.MockTransport, no network):
        - happy path, and the payload has temperature=0 + enable_thinking: false
        - fences and think tags stripped
        - timeout → LLMTimeoutError; connect error and 500 → LLMUnavailableError
        - empty content, finish_reason=length, non-JSON → LLMResponseError
        - the prompt names every table in ALLOWED_TABLES and no
          pg_/information_schema objects (keeps the prompt and the validator
          allowlist in sync)

     Tests come first (red, then green), the same way as steps 2 and 5. The PLAN
     doesn't require TDD for step 6; the tests are cheap and lock down the
     error contract that step 7 maps.
